## 1. Критично (баги, дыры в безопасности)

### 1.1 SQL‑инъекции через f‑string в идентификаторах таблиц
**Суть:**  
Практически все обращения к БД формируют SQL через f‑строки с подстановкой `table_name`, который приходит из пользовательского ввода (`username`). Примеры:  
`scripts/01_analyze_games.py`:  
```python
def get_table_name(username: str = None) -> str:
    if username:
        return f"games_{username.lower()}"
```
`scripts/04_download_player_games.py`:  
```python
self.table_name = f"games_{self.username.lower()}"
```
`core/database/db_manager.py`:  
```python
query = f'INSERT INTO "{self.table_name}" ({columns_str}) VALUES ({placeholders})'
```
В `web_app/routes.py` частично используется `get_safe_table_name` (заменяет `-`, `.`), но в скриптах анализа и во многих местах `table_name` берётся напрямую без валидации. Атакующий может передать `username = "x; DROP TABLE games;--"` и выполнить произвольный SQL.

**Зачем:**  
Полная компрометация БД: удаление/изменение таблиц, эксфильтрация данных. Критично.

**Оценка:** M  
*Решение:*  
- Создать единую функцию `build_table_name(username)` с жёсткой валидацией через regex `^[a-z0-9_]+$` и явным списком допустимых символов.
- Для безопасного цитирования идентификаторов использовать `psycopg2.sql.Identifier` или `psycopg2.sql.SQL`.
- Во всех модулях использовать только эту функцию, не конструировать имя таблицы вручную.

### 1.2 Управление секретами: `secrets.yaml`, дефолтный SECRET_KEY, утечки
**Суть:**  
- `config/secrets.yaml` содержит пароли и API‑ключи. Файл не должен попадать в репозиторий, но в дереве он отсутствует – значит либо не создан, либо игнорируется. Нужно гарантировать это через `.gitignore` и `.env.example`.
- `web_app/config.py`:  
```python
SECRET_KEY = os.getenv('SECRET_KEY', 'dev-secret-key-change-in-production')
```
Если переменная окружения не задана, используется известный дефолтный ключ, что позволяет подделывать CSRF‑токены и сессии.
- `config_loader.py` в методе `get_db_config` возвращает пароли в открытом виде. При логировании или выводе ошибок они могут попасть в логи (например, `check_db.py` печатает длину пароля, но не сам пароль – хорошо, но остаётся риск через traceback).
- Конфиг загружает `secrets.yaml` и объединяет с основным конфигом; при `print_config(show_secrets=False)` он скрывает, но сам объект `self.config` хранит секреты.

**Зачем:**  
Утечка учётных данных БД и API‑ключей. Защита от несанкционированного доступа.

**Оценка:** S (переход на env) / M (полная ревизия)  
*Решение:*  
- Убрать `secrets.yaml` из репозитория, использовать `.env` + `python-dotenv`. Добавить `.env.example`.
- В production требовать `SECRET_KEY` обязательно: при отсутствии – падать при старте.
- Для паролей использовать `getpass` / менеджеры секретов (Vault, AWS Secrets Manager) в проде.
- В логах никогда не выводить объекты конфига, содержащие секреты. Добавить фильтры в logging.

### 1.3 Фоновые задачи через `threading.Thread` в Flask
**Суть:**  
В `web_app/routes.py` при запуске анализа создаётся отдельный поток (судя по `threading` и функции `_run_analysis_task`). Это небезопасно для продакшена:
- Потоки не управляются; при перезапуске gunicorn они теряются.
- Нет ограничения на число параллельных задач кроме уникального индекса в БД, но сам индекс не решает проблему перегрузки CPU/сети/БД.
- Каждый поток создаёт свой `DatabaseManager` и соединение, что может исчерпать `pool_size`.
- При падении потока ошибка не логируется централизованно, задача остаётся `running`.

**Зачем:**  
Предотвращение деградации сервиса, гарантия выполнения задач, масштабирование.

**Оценка:** L  
*Решение:*  
- Внедрить очередь задач: Celery + Redis/RabbitMQ, RQ (если просто) или хотя бы `concurrent.futures.ThreadPoolExecutor` с ограниченным числом воркеров и мониторингом.
- Убрать ручное управление потоками, делегировать выполнение воркеру.
- Использовать единое соединение с БД через пул, а не создавать на каждую задачу.

### 1.4 Некорректное извлечение PGN‑нотации: `pgn_moves` содержит repr списка
**Суть:**  
`services/pgn_parser.py`, метод `_get_pgn_moves`:
```python
def _get_pgn_moves(self, game_node: chess.pgn.Game) -> str:
    try:
        return str(game_node.mainline_moves())
    except Exception:
        return str(game_node)
```
`game_node.mainline_moves()` возвращает список объектов `chess.Move`, а `str(list)` даёт что‑то вроде `[Move.from_uci('e2e4'), Move.from_uci('e7e5'), ...]`. Этот текст сохраняется в БД и затем передаётся в DeepSeek‑промпт. Модель не сможет понять ходы, анализ будет бесполезен.

**Зачем:**  
Работоспособность ключевой функции анализа партий.

**Оценка:** S  
*Решение:*  
Использовать экспортёр:
```python
import chess.pgn
exporter = chess.pgn.StringExporter(headers=False, variations=False, comments=False)
return game_node.accept(exporter)
```
Или вручную собрать SAN из основного варианта.

### 1.5 Неверный подсчёт количества ходов
**Суть:**  
`PGNParser._count_moves`:
```python
main_line = list(game_node.mainline_moves())
return len(main_line)
```
`mainline_moves()` возвращает количество полуходов (plies), а не полных ходов. Для партии из 40 ходов будет 80. В схеме `move_count` вероятно ожидается число полных ходов. В промпте DeepSeek это искажает информацию.

**Зачем:**  
Корректная статистика и промпт.

**Оценка:** S  
*Решение:*  
Вычислять как `game_node.end().board().fullmove_number - 1` (если начат с 1) или просто `len(main_line) // 2` с учётом цвета первого хода.

---

### 1.6 Обработка отсутствующей даты и результата в PGN
**Суть:**  
`PGNParser._parse_date` возвращает `datetime.now()` при отсутствии/некорректной дате, что молча искажает данные.  
`_determine_result` для неизвестного результата возвращает `'Draw'`, что неверно – игра с неизвестным результатом должна быть пропущена или помечена особо.

**Зачем:**  
Целостность данных, избежание ложной статистики.

**Оценка:** S  
*Решение:*  
- При отсутствии даты – пропускать игру (или сохранять с NULL, если колонка позволяет).
- При неизвестном результате – пропускать игру, логировать предупреждение.

---

### 1.7 Lichess API: неполная обработка 429 и потоковое чтение
**Суть:**  
`services/lichess_client.py`:
- При 429 выполняется `time.sleep(retry_after)` внутри цикла, но счётчик попыток не сбрасывается, что может привести к бесконечному ожиданию при постоянном 429, особенно если `retry_after` велик.
- Используется `stream=True`, но затем `response.text` загружает весь ответ в память. Для больших выгрузок (тысячи игр) это может вызвать OOM.
- Нет глобального rate limiting и уважения к заголовкам `RateLimit-*`.

**Зачем:**  
Устойчивость к лимитам API, экономия памяти.

**Оценка:** M  
*Решение:*  
- Использовать `iter_lines()` и парсить PGN потоково.
- Реализовать экспоненциальную задержку с jitter, ограничить число попыток.
- Добавить общий токен‑bucket для всех запросов к Lichess.

---

### 1.8 DeepSeek: health‑check при каждом вызове
**Суть:**  
`services/deepseek_analyzer.py` в `analyze_game` вызывает `check_health()`, который делает HTTP‑запрос к `/v1/models` каждый раз. Это лишняя задержка и нагрузка на API. При недоступности DeepSeek все задачи падают с ошибкой, но health‑status можно кэшировать.

**Зачем:**  
Снижение задержки и количества запросов.

**Оценка:** S  
*Решение:*  
Кэшировать результат health‑check на 30–60 секунд с TTL, обрабатывать ошибки при реальном вызове.

## 2. Архитектура и структура

### 2.1 Дублирование логики анализа и обработки таблиц
**Суть:**  
Скрипты `01_analyze_games.py`, `02_deep_analysis.py`, `03_analyze_opening.py`, `05_analyze_player.py`, `07_analyze_games_detailed.py` содержат почти одинаковые SQL‑запросы и логику получения статистики. Также дублируется подмена `db.table_name`. Это усложняет поддержку и ведёт к расхождениям.

### 2.2 Отсутствие миграций БД
**Суть:**  
Схема управляется YAML‑файлом и скриптом `setup_db.py`/`setup_analysis_tasks.py`. Изменения схемы не версионируются, нет отката. Ручное управление индексами, триггерами и таблицами может привести к несоответствию окружений.

**Зачем:**  
Воспроизводимость, безопасные изменения структуры.

**Оценка:** M

### 2.3 Проблема с постоянным пересозданием `DatabaseManager` и соединений
**Суть:**  
Каждая функция в `web_app/routes.py` и почти каждый скрипт создают новый `ConfigLoader` и `DatabaseManager`. В рамках одного HTTP‑запроса может быть 3–5 подключений к БД. Это истощает пул и замедляет ответ.

**Зачем:**  
Эффективное использование ресурсов СУБД.

**Оценка:** L  
*Решение:*  
- Использовать паттерн «единое соединение на запрос» (Flask `g`) или интеграцию с SQLAlchemy / Flask-SQLAlchemy.
- Настроить пул соединений (`psycopg2.pool.ThreadedConnectionPool`).
- В скриптах создавать один `DatabaseManager` и передавать его в функции.

### 2.4 Мутация `table_name` у объекта `DatabaseManager`
**Суть:**  
Шаблон:
```python
original_table = db.table_name
db.table_name = table_name
try:
    ...
finally:
    db.table_name = original_table
```
встречается повсеместно. Он не потокобезопасен и легко забывается, что приводит к обращению к неправильной таблице.

**Зачем:**  
Безопасность конкурентного доступа и читаемость.

**Оценка:** M  
*Решение:*  
Изменить сигнатуры методов `DatabaseManager`, чтобы имя таблицы передавалось аргументом:
```python
def insert_games(self, games, table_name=None)
def get_table_stats(self, table_name=None)
```
Тогда не потребуется мутировать объект. Либо создать репозиторий для конкретной таблицы.

`web_app/routes.py` содержит формы, SQL‑запросы, вызовы DeepSeek, работу с БД, обработку ошибок. Файл вырос до 53k+ символов. Это нарушает принцип единственной ответственности.

Упрощение тестирования и поддержки.

**Оценка:** M

Разделить на blueprint’ы: `players`, `games`, `analysis`, а бизнес‑логику вынести в сервисы из `services/`.

### 2.6 Импорты и зависимость `web_app` от `core`
**Суть:**  
`web_app/routes.py` импортирует `from web_app import tasks as analysis_tasks` и одновременно внутри определяет функции `get_game_for_analysis`, `save_analysis`, дублируя логику, которая частично есть в `tasks.py` и `services/deepseek_analyzer.py`. Это создаёт цикломатическую сложность.

**Зачем:**  
Чистая архитектура, избежание циклических зависимостей.

**Оценка:** M  
*Решение:*  
Вынести общую логику анализа в `services/analysis_service.py`. `routes.py` вызывает только этот сервис, а `tasks.py` остаётся только для управления очередью задач.

## 5. Производительность

### 5.1 Медленная вставка игр: построчные INSERT и SAVEPOINT
**Суть:**  
`DatabaseManager.insert_games` выполняет для каждой игры:
```python
cur.execute(f"SAVEPOINT {savepoint_name}")
cur.execute(f'INSERT INTO "{self.table_name}" ...')
cur.execute(f"RELEASE SAVEPOINT {savepoint_name}")
```
Это очень медленно при импорте тысяч игр. Также все операции обёрнуты в одну транзакцию, что может привести к огромному логу WAL.

**Зачем:**  
Скорость импорта больших объёмов.

**Оценка:** M  
*Решение:*  
Использовать `psycopg2.extras.execute_values` или `COPY FROM` для пакетной вставки. Предварительно валидировать данные и вставлять только валидные. Для дедупликации можно делать `ON CONFLICT DO NOTHING`.

---

### 5.2 Многократное открытие соединений в рамках запроса
**Суть:**  
Как указано в архитектуре, каждый вызов хелпера в `routes.py` создаёт новое соединение. Например, страница игрока может вызывать `get_player_stats`, `get_opening_stats`, `get_recent_games` – это три соединения.

**Зачем:**  
Уменьшение накладных расходов и нагрузки на PostgreSQL.

**Оценка:** M  
*Решение:*  
Переиспользовать соединение через `flask.g` или использовать пул.

---

### 5.3 Загрузка PGN целиком в память
**Суть:**  
`LichessClient.download_games` использует `stream=True`, но потом `response.text`, а `PGNParser.parse_content` читает весь файл в `content`. Для больших объёмов (например, все игры пользователя) это может вызвать MemoryError.

**Зачем:**  
Поддержка больших выгрузок.

**Оценка:** M  
*Решение:*  
Обрабатывать PGN потоково: итерироваться по `response.iter_lines(decode_unicode=True)` и по мере получения читать игры через `chess.pgn.read_game`. Для файлов – читать файл построчно, не загружая целиком.

---

### 5.4 Отсутствие пагинации в API Lichess
**Суть:**  
При скачивании всех игр (`max_games=None`) API может вернуть только ограниченное количество (обычно до 1000, настраивается в конфиге `download_limit: 1000`). Код не реализует цикл для получения следующих страниц по датам.

**Зачем:**  
Полнота данных.

**Оценка:** M  
*Решение:*  
Реализовать пагинацию с использованием параметров `since`/`until` и `max`, чтобы корректно обойти лимит.

---

### 5.5 Избыточный health‑check и отсутствие кэширования в DeepSeek
**Суть:**  
DeepSeek health‑check выполняется перед каждым анализом, что добавляет один HTTP‑запрос. Можно кэшировать состояние.

**Зачем:**  
Снижение задержки.

**Оценка:** S  
*Решение:*  
Кэшировать результат health на 30–60 сек.

## 6. Инструменты и CI

### 6.1 Отсутствие CI/CD
**Суть:**  
Нет конфигурации GitHub Actions / GitLab CI. Код не проходит автоматическую проверку при пушах.

**Зачем:**  
Раннее обнаружение ошибок, единый стандарт.

**Оценка:** M  
*Решение:*  
Добавить workflow:
- `lint`: flake8, black --check, isort --check.
- `typecheck`: mypy.
- `test`: pytest с PostgreSQL service.
- `security`: bandit, safety check.
- `build`: docker build (опционально).

---

### 6.2 Нет pre‑commit хуков
**Суть:**  
Нет `.pre-commit-config.yaml`, форматирование и линтеры не автоматизированы.

**Зачем:**  
Улучшение качества коммитов.

**Оценка:** S  
*Решение:*  
Настроить pre-commit с black, flake8, isort, bandit.

---

### 6.3 Не зафиксированы версии зависимостей
**Суть:**  
`requirements.txt` использует `>=`, что может привести к несовместимым обновлениям.

**Зачем:**  
Воспроизводимость сборки.

**Оценка:** S/M  
*Решение:*  
Перейти на `pip-tools` (requirements.in + lock) или Poetry. Зафиксировать точные версии.

---

### 6.4 Отсутствие Dockerfile и docker-compose
**Суть:**  
Развёртывание затруднено: вручную нужно ставить PostgreSQL, gunicorn, настраивать переменные окружения.

**Зачем:**  
Упрощение деплоя и тестирования.

**Оценка:** M  
*Решение:*  
Создать `Dockerfile` для приложения, `docker-compose.yml` с PostgreSQL и приложением. Добавить healthcheck для БД.

---

### 6.5 Makefile: устаревшие цели
**Суть:**  
`make test` ссылается на `tests/`, которого нет. `make init` вызывает `scripts/init_project.py`, который создаёт venv и устанавливает зависимости, но эта логика частично дублируется Docker/pre-commit. Нужно пересмотреть набор целей.

**Зачем:**  
Актуальные команды разработчика.

**Оценка:** S  
*Решение:*  
Обновить Makefile: добавить цели `lint`, `format`, `typecheck`, `test`, `docker-up`, `docker-down`. Убрать или переработать `init`.
